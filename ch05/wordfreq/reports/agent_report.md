# wordfreq Python → Rust 이식 보고서

작성일: 2026-10-28
툴체인: cargo 1.99.1 (Rust 표준 라이브러리 Unicode 17.0.0)

## 결론

Rust 구현(`rust_app/`)은 작성했습니다. 완료 조건 1~4는 통과했지만 **5(compare.py)는 실행 파일이 운영체제 정책에 막혀 확인하지 못했습니다(종료 코드 3)**.
따라서 이 작업은 **완료가 아닙니다**. Python과의 바이트 단위 일치는 아직 검증되지 않았습니다.

## 완료 조건 결과 (모두 `rust_app/`에서 직접 실행)

| # | 조건 | 결과 |
|---|---|---|
| 1 | `cargo build --release` | 통과 |
| 2 | `cargo fmt --check` | 통과 |
| 3 | `cargo clippy --all-targets -- -D warnings` | 통과 |
| 4 | `cargo test` | 통과 (단위 테스트 17개, `src/lib.rs`) |
| 5 | `uv run python automation/compare.py` | **확인 못 함: 종료 코드 3**. 첫 케이스(`basic`)에서 `rust_app\target\release\wordfreq.exe: [WinError 4551] 애플리케이션 제어 정책에서 이 파일을 차단했습니다`. 두 번 빌드해 두 번 실행했고 결과가 같았습니다 |

4번 관련: 처음에는 `cargo test`가 바이너리 대상(`main.rs`)의 빈 테스트 실행 파일과 `rustdoc.exe`(doctest)를 실행하다가 같은 4551 오류로 실패했습니다.
`main.rs`에는 테스트가 없고 `lib.rs`에는 문서 테스트가 없으므로 `Cargo.toml`에서 `[[bin]] test = false`, `[lib] doctest = false`로 두 단계를 끄고 다시 실행했습니다.
실제 단위 테스트(라이브러리 테스트 실행 파일)는 정책에 막히지 않고 실행됐습니다.

## 구현 요약

- `src/lib.rs`: 로직만 둡니다(파일·표준 입출력 접근 없음). `tokenize`, `to_lower`, `count_words`, `format_text`, `format_json`, `parse_args`, `parse_top`
- `src/main.rs`: 인자 해석 결과 처리, 파일 읽기, 오류 메시지, 종료 코드(0/1/2), stdout에 UTF-8·LF 바이트 출력
- 외부 크레이트 없음, edition 2024

계약 대응:

- **공백(2.2)**: Python `str.split()` 기준 문자 집합을 직접 정의했습니다. U+0009–000D, U+001C–001F, U+0020, U+0085, U+00A0, U+1680, U+2000–200A, U+2028, U+2029, U+202F, U+205F, U+3000입니다. Rust `char::is_whitespace`와 달리 U+001C–001F를 포함합니다
- **문장 부호(2.3)**: ASCII 32자와 `“ ” ‘ ’ … ·`를 앞뒤에서만 떼어 냅니다(`trim_matches`)
- **소문자(2.4)**: Rust `str::to_lowercase`를 씁니다. 이 함수도 SpecialCasing(예: `İ` → `i̇`)과 어말 시그마 규칙을 따릅니다. 다만 Unicode 버전 차이를 보정합니다(아래 가정 3)
- **정렬(3절)**: 빈도 내림차순, 같은 빈도는 UTF-8 바이트 순서로 정렬합니다(코드 포인트 순서와 같음)
- **JSON(3절)**: `ensure_ascii=False`와 같게 `"`, `\`, U+0000–001F만 이스케이프합니다(`\b \f \n \r \t`는 짧은 형태, 나머지는 소문자 `\u00xx`)
- **오류(4절)**: 파일 없음(`ErrorKind::NotFound`) → `file not found`, 그 밖의 읽기 실패 → `cannot read file`, UTF-8 디코딩 실패 → `not valid UTF-8`, 종료 코드는 모두 1입니다. 인자 오류는 사용법 한 줄과 오류 한 줄을 stderr에 쓰고 종료 코드 2로 끝냅니다

## 직접 정한 가정

1. **`--top` 값**: ASCII 숫자(`[0-9]+`)만 받습니다. `05`는 5로 받고, `+5`, ` 5`, 전각 숫자, 밑줄, 음수는 인자 오류로 봅니다(AGENTS.md 지시). `usize` 범위를 넘는 큰 값은 "전부 출력"과 같으므로 `usize::MAX`로 포화시킵니다(Python은 임의 정밀도 정수로 받아 같은 결과를 냅니다)
2. **인자 해석**: `--top N`, `--top=N`, `--json`, `--`(옵션 끝), `-h`/`--help`(사용법을 stdout에 쓰고 0으로 종료)를 지원합니다. 옵션은 FILE 앞뒤 어디에나 올 수 있고, 같은 옵션이 반복되면 마지막 값을 씁니다. 다음은 argparse의 부수 동작이므로 재현하지 않았습니다
   - 옵션 이름 줄여 쓰기(`--to`, `--js`)
   - `-5`처럼 음수 모양 인자를 위치 인자로 받는 규칙. Rust 구현에서는 `-`로 시작하는 두 글자 이상의 인자를 모두 옵션으로 보고, 모르는 옵션이면 오류를 냅니다. 이런 파일 이름은 `--` 뒤에 쓰면 됩니다
   - 공백이 든 `-` 시작 인자를 위치 인자로 보는 규칙
3. **Unicode 버전 보정**: 기준 Python 3.12는 Unicode 15.0, Rust 1.99 표준 라이브러리는 17.0입니다. Rust 표에서 소문자 매핑이 있는 문자를 모두 스캔했고, 15.0 이후에 생긴 대소문자 문자를 `UNKNOWN_TO_PYTHON` 표로 정리했습니다
   - 대상: `1C89–1C8A`, `A7CB–A7CF`, `A7D2`, `A7D4`, `A7DA–A7DC`, `A7F1`, Garay `10D50–10D65`·`10D70–10D85`, Beria Erfe `16EA0–16EB8`·`16EBB–16ED3`
   - 이 문자들은 소문자로 바꾸지 않습니다. 시그마 어말 판정에서는 Python이 미할당 문자를 보는 방식처럼 cased도 case-ignorable도 아닌 경계로 취급합니다(문자열을 그 자리에서 끊어 변환)
   - 툴체인의 Unicode 버전이 바뀌면 이 표를 다시 점검해야 합니다. 이를 알리도록 `char::UNICODE_VERSION == (17, 0, 0)`을 단언하는 테스트를 넣었습니다
4. **파일 경로**: 사용자가 준 문자열(OsString)을 그대로 엽니다. pathlib의 경로 정규화(아래 의심 사항 1)는 재현하지 않았습니다. 오류 메시지의 `<FILE>`은 입력 문자열을 그대로 쓰고, UTF-8로 바꿀 수 없는 인자는 손실 변환(U+FFFD)합니다
5. **stdout 쓰기 실패**(파이프 끊김 등): 종료 코드 1로 조용히 끝냅니다. 계약에 없는 상황입니다

## 기준 구현 의심 사항

기준 파일은 고치지 않았습니다.

1. **경로 정규화(pathlib)**: `Path(args.file)`이 경로를 정규화합니다. 예를 들어 빈 문자열 `""`은 `.`(디렉터리)이 되어 `cannot read file`이 나지만, Rust는 `file not found`를 냅니다. `basic.txt/`처럼 끝에 구분자가 붙은 경로도 Python은 잘라 내고 정상으로 읽습니다. 계약 4절은 이 경우를 정하지 않았습니다. 의도한 동작인지 계약에 적어 주는 편이 좋겠습니다
2. **계약 2절이 Python 버전에 묶여 있음**: "Python `str.split()`/`str.lower()`와 같다"는 정의는 Python의 Unicode 버전에 따라 결과가 달라집니다(3.12 = 15.0, 3.13 = 15.1, 3.14 = 16.0). 계약 문서 자체에 Unicode 버전(15.0)을 적어 두면 재구현 기준이 분명해집니다
3. `cases.json`에는 Unicode 버전 차이, U+001C–001F 공백, 그리스 어말 시그마, JSON 제어 문자 이스케이프를 다루는 케이스가 없습니다. 위 규칙은 현재 비교 케이스로는 검증되지 않습니다(Rust 단위 테스트로만 확인)

## 하지 못한 것과 이유

1. **완료 조건 5 미확인**: Windows 애플리케이션 제어 정책(스마트 앱 컨트롤, WinError 4551)이 `target\release\wordfreq.exe` 실행을 막았습니다. AGENTS.md 지시에 따라 코드를 고치거나 우회하지 않았습니다. 정책을 허용하거나 다른 환경에서 `uv run python automation/compare.py`를 다시 실행해야 합니다
2. **Unicode 전 범위 대조 미수행**: 공백·소문자·시그마 규칙을 모든 코드 포인트에서 Python 3.12와 직접 대조하지 못했습니다. compare.py에 `--cases`로 별도 케이스를 주는 방법이 있지만, Rust 실행 파일이 막혀 쓸 수 없었습니다. 셸에서 Python을 직접 실행하는 것은 허용되지 않습니다. Unicode 15.0 데이터 파일(예: Git for Windows의 Perl `unicore`)을 읽는 것도 권한이 없어 하지 않았습니다. 그래서 가정 3의 표는 Rust 쪽 표 스캔과 Unicode 16.0·17.0 추가 문자에 대한 지식으로 만들었습니다
3. **남은 이론적 차이**: 16.0·17.0에서 새로 생긴 문자 중 대소문자 매핑은 없지만 case-ignorable(새 결합 부호 Mn 등)이거나 Lowercase 속성만 가진 문자는 표에 넣지 않았습니다. 이런 문자는 대문자 `Σ` 바로 옆에 올 때만 결과(`σ`/`ς`)에 영향을 줍니다(예: 그리스 문자 + 새 결합 부호 + `Σ`). 실행이 허용되면 전체 코드 포인트를 담은 케이스 파일로 compare.py를 돌려 확인하기를 권합니다
